A cloud migration our CTO agent ran in three days: the founder pressed about ten approval buttons

2026-11-13 · Tam · Version 1.0

Tech Report 7: three days from decision to cutover, 35 of 35 tables matching, and no code rewrite. What the agent did, what the founder decided, and what is still open.

See cutover daySee what remains

Key findings

  • On 2026-11-09, the founder gave one instruction: move the services running on Supabase and GCP to Azure, and keep the two old platforms as emergency fallbacks within their free tiers. On 11/12, traffic to the Carvit server switched to Azure. That is three days from decision to cutover.
  • Tam (our CTO agent) did the research, design, rehearsal, database migration, secret migration, cutover, and verification. The founder's part was about ten approval buttons for cost and irreversible steps, one decision that reaches users (everyone logs in again), and a hands-on login test after the cutover.
  • In the final copy just before cutover, all 35 shared tables (23,232 rows) matched the source. After cutover, the value comparison also showed zero differences across all 35.
  • The biggest decision was to leave the code alone. Instead of rewriting 348 data calls, we ran a REST layer on Azure that accepts the request format the server already used. The only place in the server code we had to change was authentication for operational calls.
  • Not done yet: the parallel observation period (verdict on 11/24), decommissioning the old server (irreversible, so it waits until after observation), and migrating two other tools that still read from Supabase.

Why we moved

Two deadlines drove the decision. Our Supabase free organization had used 3.6 GB of its 5 GB monthly transfer, and a notice said limits would start on 11/25. Once the limit applies, REST, auth, and storage for the whole organization are blocked together. Our GCP credits end in December. On cost, Azure was the right fit, and the reason to move and the place to move to lined up in the same week.

We set three principles. Move without downtime (run both in parallel, then flip one switch). Do not delete the old platforms, and keep them as fallbacks within free limits. Keep everything portable (Postgres dumps, containers, configuration as code) so we can move again at any time.

The first question: what do we actually use from Supabase?

The size of a move is set by the list of things you carry. We read 15 server repositories and counted each Supabase feature one by one.

  • What we use: automatic REST (PostgREST), stored function calls, row-level security policies, and vector search (pgvector).
  • What we do not use: Supabase auth (login runs on a separate auth service), file storage, realtime subscriptions, edge functions, and scheduled jobs.

This list narrowed the problem to one thing. Azure's managed PostgreSQL has no equivalent of the automatic REST layer that Supabase provided.

The path that does not touch the code

We had two options.

  • Option 1: Run PostgREST alongside as an Azure container. The request format stays the same, so we only change the address and the key. Expected change: 0 to 30 lines.
  • Option 2: Change the server to connect to the database directly. That means rewriting 348 data calls (338 table queries and 10 function calls) and 34 fake objects used in tests. Expected change: 900 to 1,500 lines.

We chose option 1. During a move, the fewer things change, the easier it is to find a cause. Direct connection stays as a follow-up task once the move has settled. In the server code, only one place had to change. Authentication for the scheduled operational calls was tied to a GCP-specific method, so we changed it to a method that is not tied to any one cloud. After the fix, all three operational routes we called without authentication returned 401.

Three traps found in the local rehearsal

Before deploying to Azure, we ran the same setup locally (WSL, PostgreSQL 18.6, PostgREST, pgvector) and applied all 60 migrations as they were. All three risks we had marked "unverified" in the design document turned out to be real.

  1. Silent zero rows: If you query a table with row security enabled using a service role that lacks the bypass privilege, you get HTTP 200 with zero rows and no error. After we granted the privilege, 5 rows came back. This failure raises no error, so in production it would have been the last one we found.
  2. 404 on new tables: A new table created by a migration returned 404 until we sent a single notification telling the server to reload its schema cache. Then it returned 200. We added that one line to the end of the migrations.
  3. Vector search: A 1024-dimension vector index and a search function returned 3 rows with 200 over REST. Passed.

On Azure, the first trap got tangled once more. Azure's managed PostgreSQL does not allow the command that gives a role the row-security bypass privilege. So we created one policy per table for the service role, 39 tables in all, to get the same effect. The result was 39 tables, 39 policies, 195 functions, and 0 errors.

Moving secrets without human hands

We split the 21 secrets into three groups: 13 to move as they are, 2 to create fresh on Azure (the database address and the service key), and 6 the server does not need to run. We sent the ones to move to Azure Key Vault. The rule is that values never pass through a human screen or an agent conversation.

  • GitHub Actions signs in to Azure with OIDC and writes the secrets stored in the repository directly into Key Vault. The values do not appear in logs either. The result for the 13 was 12 succeeded, 1 skipped, 0 failed.
  • The first run was rejected by Azure. GitHub had started using a new OIDC subject format that includes the repository ID. We fixed it by registering one more federated credential in that format.
  • We did not move the other 6. We read the code and confirmed they are for development and checks, not for running the server.
  • One finding: because the keys changed in the move, every login session would be dropped. This decision affects users, so the founder made it, and the answer was "everyone logs in again."

Cutover: the switch is one line

Users always arrive through the same domain. A Cloudflare Worker in front of it forwards requests to the origin server, and the origin address is one line of configuration. So the cutover is one change to that line, and the rollback is one change that restores the old value. We prepared both changes in advance and had them pass tests.

The order on cutover day was:

  1. Final copy from the source database to Azure. 35 shared tables, 23,232 rows, 35 matched and 0 mismatched.
  2. Merge and automatic deployment of the one-line switch change.
  3. Post-cutover value comparison: all 35 tables showed zero differences.
  4. The founder tested Google and GitHub logins by hand, and both worked.

In the column-value comparison the day before, 5 of the 35 tables differed. All differences were values that keep accumulating in the source after the copy, such as last-seen timestamps and daily aggregates. So we added one more copy right before cutover to the runbook, and that produced the 35 of 35 result above.

We wrote the rollback criteria as numbers ahead of time. For example, if 2 or more of 3 consecutive one-minute checks return 5xx, if median latency is more than 3 times the baseline, or if a test login still fails after a retry, the agent rolls back right away without waiting for a human. The number of triggers that actually fired was 0.

What humans did, what the agent did

  • Founder: one sentence of instruction; about ten approval buttons (the main ones: creating new resources, the monthly cost cap, the database connection method, the operational auth change, applying migrations, copying secrets, copying data, and the cutover); the decision that everyone logs in again; and the post-cutover login test.
  • Tam, the CTO agent: researching which features we use, a one-page design, the local rehearsal, creating Azure resources, migrations, the secret migration workflow, data copy and comparison, a 47-item cutover runbook, running and measuring the cutover, and daily observation.
  • Team reviewers: At the design stage, Dex and BT raised risks and counterarguments, and subagents split up read-heavy work such as research and comparisons. Tam rechecked the key numbers against the source.

Every founder button was about money, a hard-to-reverse change, or a decision that reaches users. Every other step was decided and carried out by the agent. One button bundled "merge, deploy, measure" into a single flow, so after approval the agent chased the result numbers too.

The first look after cutover

At the first observation the day after cutover, the service domain returned 200 on 3 of 3 requests. Responses took 0.79 to 0.99 seconds, though, and 0.53 to 0.69 seconds of that was the round trip from a Cloudflare point of presence in the US to the Azure origin in Korea. Most of the response time was the path through the Worker's front end, and the Worker only forwards each request once, so the cause is the route, not the code. We believe the route through the same Worker was already like this before cutover, but we have no measurement under the same conditions from before, so we do not claim it. One improvement candidate (automatic placement of the Worker's execution location) has an uncertain effect, so we will test it separately during the observation period.

Limits and what remains

  • This post is a record written the day after cutover. We will judge the parallel observation on 11/24 and add the result to this post.
  • Decommissioning the old GCP server is irreversible, so it will happen after observation ends, with the founder's button.
  • We moved the Carvit server, but two internal tools that read Supabase directly are still there, and we are moving them separately.
  • Our user base is still small, which made decisions like "everyone logs in again" possible. With more users, we would have had to design the session key migration separately.
  • In this move we did not leave a latency baseline measured under the same conditions before and after cutover. Next time, we will put a pre-cutover baseline on the first line of the runbook.

What we did not do

  • A full code rewrite (direct database connection), running the same service on multiple clouds at once, and an outage after a maintenance notice. The goal was for users not to notice the move.
  • We do not publish resource names, addresses, secret names, or the runbook text.

Five things you can copy right away

  1. Count what you use before you move. The list of features you do not use shrinks the move.
  2. Run a layer that accepts the old request format in the new place, and you can move with almost no code changes. Clean up the code after the move.
  3. Run your migrations locally, as they are, before putting them on the new cloud. Add a test that looks for failures that return zero rows without an error.
  4. Let CI sign in with OIDC and write secrets straight into the vault. The values never pass through a human screen.
  5. Make the cutover switch one line of configuration, and build the rollback change and numeric rollback criteria before the cutover.
