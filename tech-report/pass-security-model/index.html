What Carvit Pass protects, and what it does not.

2026-10-03 · Tam · Version 1.0 (draft)

Tech Report 3: the security model of a vault that lets AI agents use your keys without seeing them. Scope first, then how the keys are layered, how an agent uses one, and the threats we have and have not answered.

See the threatsHow the keys are layered

Key findings

  • Carvit Pass protects a value up to the moment it leaves the drawer: one key, only to an allowed target, with approval and a log.
  • It does not protect what happens after the value leaves, an agent that is already tampered with, or a device that is already compromised.
  • The drawer key is wrapped by two shares, one derived from the PIN on the device and one held by the server. Stealing the server’s encrypted copy or the device’s wrapped key alone does not let anyone guess the PIN.
  • An agent never receives a value. A local helper types it into the allowed target, and anything that cannot be undone needs a tap on the owner’s phone.

What it protects, and what it does not.

“A value is safe until it leaves the drawer. After that, it is only as safe as whoever receives it.”

Carvit Pass keeps keys for people who work with AI agents. We state its scope first because a vault that promises everything protects nothing.

It protects: a value up to the moment it leaves the drawer. When it leaves, it is one key, going only to an allowed target, with the owner’s approval where needed and a record afterwards.

It does not protect: what the receiver does with a value afterwards, an agent that is already tampered with, or a device that is already compromised. Password managers draw the same line.

Telling a tampered agent apart from a fooled one is an open research problem for us. We do not claim to solve it.

Two shares, one drawer key.

Values are encrypted on the user’s device, in the browser extension, and nowhere else. The server only ever holds ciphertext.

1

The drawer key

A random 512-bit key. The first 256 bits encrypt each value with AES-GCM. The last 256 bits make a keyed fingerprint used to detect duplicates.

2

Wrapped by two shares

The drawer key is stored wrapped by a key built from two parts: one derived from the PIN (PBKDF2-SHA256, 600,000 rounds, computed on the device only) and one the server holds and releases only for the right PIN.

3

Locked after five misses

The server stops releasing its share after five wrong PINs. Without the server’s share, a PIN cannot be guessed offline from the device’s copy, and the server’s ciphertext alone cannot be opened.

Figure 1. The three steps between a PIN and a value.

An unlocked drawer lives in browser memory only and disappears when the browser closes or the drawer is locked. Each item also records a format version and which drawer it belongs to (added 2026-10-03), so shared drawers can be added later without re-encrypting values.

An agent uses a key without seeing it.

An agent never receives a value. It asks the local helper to put one named key into one named target, and the helper takes the value out of the drawer, types it into the target and discards it. Only a short fingerprint of the value is logged.

Targets are an allow-list: one settings file and named repository secrets. Anything else is refused before approval is even asked.

Risk decides the approval. Actions that can be undone, such as putting an ordinary key into a settings file or registering a new secret, run without asking and send a silent notice. Actions that cannot be undone, such as overwriting an existing secret or using a key marked as money or admin, need a tap on the owner’s phone. “Can be undone” means it can be deleted, not that it is safe. A tampered agent is outside this scope.

The approval comes from a dedicated bot. Only a button press from the owner’s own account, matching a one-time number made for that request, counts, and it expires after five minutes. These are current settings, not fixed promises: after one approval the same agent may repeat the same action for two hours (extended on use, at most twelve), ending when the drawer locks, and approval requests are limited to three per ten minutes to avoid approval fatigue.

What we are not doing yet.

  • Team sharing, where a drawer key is wrapped to each member’s public key, per-item keys, recovery and single sign-on. We keep the storage format ready for shared drawers but have built none of it.
  • Opening a drawer with a phone approval instead of the PIN. We will revisit it before outside users arrive, or sooner if the PIN proves too frequent.
  • A confirmation code matching the agent’s screen to the approval message, and regular rotation of the approval bot’s credential. We add both when money or admin keys go into the vault.
  • An independent security audit and open-sourcing the encryption core. We plan both before public users.

What we did not prove.

  • This is a description of the design from reading the code. It has not been audited by anyone outside and we have not run a penetration test.
  • The review by a second AI model covered the written design, not a running system.
  • We have not measured how often the PIN has to be entered, which decides how soon phone-approved unlocking is worth building.
