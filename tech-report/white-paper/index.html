Background & Origin Story

“Can the autonomy and judgment we get from a frontier agent such as Claude Code with Sonnet be reproduced with a smaller or open model such as the ones we run through Hermes, if we put a strict output format and guardrails around it?”

Carvit started from that question. Frontier cloud models show strong autonomous execution. We wanted to know how much of it other models can deliver when they are not trusted to write files or run commands directly, and a strict output format plus guards decide what is allowed to happen.

This paper is the first measurement we can show, and it is deliberately small: fixing lint errors in Python files. The first runs looked like successes, with zero lint errors, and were not. A docstring had vanished, a function call was gone, a function body had attached itself to the function above. That is where our position took shape: reliability comes from a strict output format, guardrails and deterministic verification, not from model size alone.

What we have not shown: that this holds for hard, open-ended tasks, or beyond a single 14B model on our own hardware. The two main models here, Upstage Solar-pro4 through the Hermes Agent runtime and Llama 3.3 70B through OpenRouter, were called through hosted APIs, and one local replay followed. The question above is still open, and this paper is the first step toward answering it.

Passing lint is not the same as staying correct.

We asked two models to fix lint errors in small Python files and scored them with a linter. Three failure shapes passed the linter while damaging the code:

  1. Deleting a def line alone. The function body attached itself to the function above as dead code. Syntax and ruff passed, the behavior changed. This false PASS happened in 4 of 4 Solar-pro4 runs on a duplicate-function target before we added a guard.
  2. Dropping the docstring or shebang while rewriting a whole file. In a 10-run format baseline, 4 of 20 attempts did this; the AST check caught them.
  3. Deleting a whole line that contained a call (an unused variable assigned from a function call). The linter is happy; the side effect is gone. Guards rejected this 21 times across both rounds (11 in Round 1, 10 in Round 2).

Three layers between a model and your file.

The model never writes the file. It proposes a small patch, and code decides whether the patch is allowed.

1

Constrain the output

Tools are turned off for the model. It may only answer with a JSON patch: a single-line edit, or a range delete of one duplicate function. No free-form code.

2

Check before applying

Only lines the linter flagged (F401, F811, F841) can change. No new identifiers. No deleting a line that calls a function. No editing a block header. A range must match exactly one undecorated earlier duplicate function.

3

Verify after applying

The result must parse, keep every top-level function and class, and pass ruff with the F rules. Saved training samples are replayed offline against the same guards.

The mixed target is the honest weak spot. Neither model passed it on the first try in either round (0 of 8 per round across both models). Their first instinct is to delete the line that holds a call, and the guard turns that into a retry.

Local replay on our own GPU

After the two hosted-API runs, we repeated the same benchmark on our own hardware: an RTX 4090 running qwen2.5-coder:14b through Ollama on localhost, with no hosted API in the loop. Four targets, eight runs each, 32 runs in total, with the Round 2 patch format and guards unchanged and no prompt tuning.

Mixed target: first try, then final

The mixed target behaved the way it did for the hosted models. On the first attempt the 14B model answered with an edit that deleted the line holding a call (parsed = re.compile(...)), and the guard rejected it before the file changed. We captured the first answer in three separate spot checks, and each one deleted that line. The rejection reason went back to the model as a note. On the second attempt it removed only the unused variable and kept the call, and all eight runs passed. The other three targets passed on the first try in 8/8 runs each.

What this suggests: even when a small local model's first answer is wrong every time on one target, a fixed set of checks plus a specific rejection note got it to the correct patch within this benchmark. What it does not show: one 14B model, four synthetic targets, and no latency or cost measurement, so it says nothing about real repositories or larger workloads.

What we did not prove.

  • Small samples: four runs per target, four targets, two models. The gap between 12/16 and 14/16 can be noise.
  • The targets are synthetic files we wrote to exercise specific lint rules. Real repositories will differ.
  • Only the pyflakes rule family (F) was scored. Style rules were out of scope.
  • The guards and prompt changed between and inside the rounds. Solar-pro4 Round 1 combines three measurement batches taken as the guards evolved. Changing one prompt line once dropped a passing target from 4/4 to 0/4 for Llama, so we re-measured the affected targets after later changes.
  • Cost and latency were not measured. The parameter count of Solar-pro4 was not verified, so this paper makes no claim about model size beyond Llama 3.3 70B being 70B.
  • Llama was called at temperature 0. The runtime settings for Solar-pro4 were left at their defaults and not recorded.
  • The two main models ran through hosted APIs: Solar-pro4 (through the Hermes Agent runtime) and Llama 3.3 70B (through OpenRouter). The only local run is the single 14B replay above (qwen2.5-coder:14b, one GPU, 32 runs). We did not test other local models or measure latency.
