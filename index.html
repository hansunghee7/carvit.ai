Background and origin

This paper began as a maintenance chore. We wanted a local model to take over a repetitive job, fixing lint errors in small Python files, so that a more expensive agent would not have to. The first runs looked like successes: the linter reported zero errors. Then we compared the files. A docstring had vanished, a function call was gone, a function body had attached itself to the function above. Every one of those passed the linter.

That changed the question. It stopped being which model is best and became what has to stand between a model and a file, so that a passing score means the code is still correct. The answer we measured is in the sections below: a narrow output format, and guards written as code.

It is also our position on agents in general: reliability comes from a strict output format, guardrails and deterministic verification, not from model size alone. Two models and four small targets do not prove that position, so this paper reports what we measured and what we did not.

Passing lint is not the same as staying correct.

We asked two models to fix lint errors in small Python files and scored them with a linter. Three failure shapes passed the linter while damaging the code:

  1. Deleting a def line alone. The function body attached itself to the function above as dead code. Syntax and ruff passed, the behavior changed. This false PASS happened in 4 of 4 Solar-pro4 runs on a duplicate-function target before we added a guard.
  2. Dropping the docstring or shebang while rewriting a whole file. In a 10-run format baseline, 4 of 20 attempts did this; the AST check caught them.
  3. Deleting a whole line that contained a call (an unused variable assigned from a function call). The linter is happy; the side effect is gone. Guards rejected this 21 times across both rounds (11 in Round 1, 10 in Round 2).

Three layers between a model and your file.

The model never writes the file. It proposes a small patch, and code decides whether the patch is allowed.

1

Constrain the output

Tools are turned off for the model. It may only answer with a JSON patch: a single-line edit, or a range delete of one duplicate function. No free-form code.

2

Check before applying

Only lines the linter flagged (F401, F811, F841) can change. No new identifiers. No deleting a line that calls a function. No editing a block header. A range must match exactly one undecorated earlier duplicate function.

3

Verify after applying

The result must parse, keep every top-level function and class, and pass ruff with the F rules. Saved training samples are replayed offline against the same guards.

The mixed target is the honest weak spot. Neither model passed it on the first try in either round (0 of 8 per round across both models). Their first instinct is to delete the line that holds a call, and the guard turns that into a retry.

What we did not prove.

  • Small samples: four runs per target, four targets, two models. The gap between 12/16 and 14/16 can be noise.
  • The targets are synthetic files we wrote to exercise specific lint rules. Real repositories will differ.
  • Only the pyflakes rule family (F) was scored. Style rules were out of scope.
  • The guards and prompt changed between and inside the rounds. Solar-pro4 Round 1 combines three measurement batches taken as the guards evolved. Changing one prompt line once dropped a passing target from 4/4 to 0/4 for Llama, so we re-measured the affected targets after later changes.
  • Cost and latency were not measured. The parameter count of Solar-pro4 was not verified, so this paper makes no claim about model size beyond Llama 3.3 70B being 70B.
  • Llama was called at temperature 0. The runtime settings for Solar-pro4 were left at their defaults and not recorded.
